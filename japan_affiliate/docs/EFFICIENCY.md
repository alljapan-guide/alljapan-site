# 効率化の設計（「公式で確認できた事実だけ公開」を、遅くせず続けるために）

課題: 事実を1つずつ人が確認すると遅い。確認を機械に任せ、人は「異常が出たときだけ」見る形にする。

| 工夫 | 何が減るか | 仕組み |
|---|---|---|
| 事実を1回だけ登録し、全記事で使い回す | 調べる手間・API費用 | 記事は `{{fact:id}}` で値を呼ぶだけ。複数記事で共有でき、記事ごとに再調査しない |
| 値が変わっても記事を書き直さない | 更新作業 | 値は登録表から表示されるので、表を直せば全記事が変わる |
| 確認は機械が毎日実行 | 人の確認 | 公式ページに値が載っているかを全事実で自動チェック。人の作業はゼロ |
| 自動修復（`verify --heal`） | 失敗時の手作業 | ページと合わなくなった事実は、公式サイトだけを検索するClaudeが新しい文言を提案し、**新しいページに実在する場合のみ**採用。変更内容は実行ログに一覧表示（これだけ見れば足りる） |
| 準備ができたトピックから書く | 止まる時間 | 事実が足りないトピックは飛ばして次へ。1本のせいで全体が止まらない |
| 調査は「先読みバッファ」だけ | API費用 | 書ける状態のトピックが3本未満のときだけ調査。満たしていればAPIを呼ばない |
| 生成に渡す事実を絞る | API費用・誤引用 | そのトピックに関係する事実だけをプロンプトに載せる |
| 失敗記事は破棄して次へ | 手戻り | ゲートに落ちた記事は公開せず、他の記事の公開は続ける |

## あなたの作業時間の目安
- 初期設定（手順書のステップ1〜9）: 合計3〜4時間、1回だけ（提携先の審査待ちは別）。
- 通常運用: 週15分（実行ログの `FAIL` と `CHANGED BY HEAL` を見る、Search Console を確認）。
- 異常があるときだけ、ログをClaudeに渡して直す。

## この設計の限界
- 自動修復は「公式ページに文言が実在する」ことしか確認できません。意味の取り違え（たとえば「対象外」が「対象」に変わった）は、`CHANGED BY HEAL` の一覧で人が拾います。
- 公式サイトが画像やスクリプトだけで表示するページは、文字として取得できず確認に失敗します。その事実は使えません。
